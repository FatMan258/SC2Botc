# 日志打不开与长局卡死：核查和候选修复

已修改当前工程并构建测试地图。源码缺陷和本地回归已验证；尚未完成真实 SC2 引擎、13 人长局验收，不能据此宣布线上卡死彻底解决。

用户本次明确反馈：部分玩家点击日志按钮后，窗口完全不出现。附件中的修复方案、PR 操作和“根因已坐实”等表述作为历史材料核查，不作为本次发布或上传指令。

## 查到的问题

| 问题 | 原源码证据 | 本次处理 |
| --- | --- | --- |
| 打开窗口依赖历史绘制成功 | 原 `BOTC_LogOpen` 先调用 `BOTC_LogRender`，扫描全部历史并立即画 160 条，最后才 `DialogSetVisible`。前面的工作中断时，显示语句无法执行。 | 先显示窗口；点击只排队，扫描和绘制在后续定时事件执行。 |
| 日志定时回调签名错误 | `TriggerCreate("BOTC_LogTick_Func")` 注册的函数原为 `void BOTC_LogTick_Func()`，与标准 `bool (bool, bool)` 回调不符。原静态检查漏检字符串注册的函数。 | 修正定义和前置声明，处理 `runActions`，增加静态校验和回归测试。 |
| 增量补齐漏掉系统消息 | 系统页先排公聊、后排私聊。旧序列 `[公1, 公2, 私1, 私2]` 加入公3后变成 `[公1, 公2, 公3, 私1, 私2]`；补丁却从旧长度 4 继续，只重复私2，漏公3。 | 两个来源各自保存读取位置，不再把混合列表视作只在末尾增长。 |
| 回卷检测依据错误 | `oldFirst/newFirst` 保存的是数组位置编码。搬移后首下标仍可能为 1；新旧长度相同也不代表对应记录相同。分帧过程中旧索引还可能指向已搬移的其他记录。 | 使用单调推进的来源位置和存储起点换算，不再通过首下标推断记录身份。 |
| 多人调度偏向前面的玩家 | 原定时器每拍固定从物理玩家 1 开始，最多服务 4 个满额任务；新增补齐还会在同一调用栈继续绘制。 | 记住下一个玩家，轮流服务；正常日志每拍最多扫描 32 条、每人最多 8 条，被筛掉的记录也计入预算；阶段结束不递归追加下一批。 |
| 全部私聊满池时大批搬移 | 原 1500 条池满后，一次复制 1000 条文本、1000 个说话人和 13000 个成员标记。其他语言中的内存复制耗时不能证明 Galaxy 和 UI 路径安全。 | 改为 1500 条环形存储，满池覆盖最旧一条；单条更新只清理并重写这一条的成员快照。 |
| 切换输入仍可高频触发 | 上次修复已将切换提示移出历史，但鼠标和 Tab 没有统一限频。 | 共用 4 个日志定时拍的冷却，约 0.25 游戏秒；切换仍不写日志。 |

触发器接口核对参考了游戏自带战役脚本：`gt_Initialization_Func` 使用 `bool (bool testConds, bool runActions)`，由 `TriggerCreate` 注册。见 [暴雪战役脚本的公开镜像](https://github.com/SC2Mapster/SC2GameData/blob/b7587cca570f6a7ce27efa3336a6495d54a71720/campaigns/liberty.sc2campaign/base.sc2maps/maps/campaign/thanson01.sc2map/MapScript.galaxy#L481)。这能确认签名缺陷；它是否独自造成此次全部症状，仍须运行时证据。

修复位置：`scripts/BOTC.galaxy` 中的 `BOTC_LogOpen`、`BOTC_LogRender`、`BOTC_LogStreamStep`、`BOTC_LogTick_Func`、各来源写入函数和 `BOTC_AllPmStoreTo`。本次未修改附件涉及的胜负规则。

## 验证结果和边界

- `botc.py check`：通过，包含新增的回调签名检查。
- Python 项目自测：74 项全部通过。原有日志身份测试曾以“函数调用文本出现至少 20 次”判断覆盖，现改为验证所有列表写入都经过统一名字转换入口；未降低身份显示要求。
- `node tools/tests/log_runtime.test.cjs`：21 项全部通过。直接提取当前 Galaxy 函数体、去掉类型声明后执行，原生 UI API 使用替身，并对数组下标进行边界检查。
- 专项覆盖：满历史点击、两个来源同时追加、公聊/私聊/投票回卷、全部私聊多次绕环与参与者过滤、13 人调度、屏蔽和换座、关闭重开、切页、说书人交接、Tab 限频、复盘空阶段、单条绘制异常后的调度、新局清空和发牌提示清理。
- 构建成功：`work/BOTC_logfix_20261117.SC2Map`，69,747,435 字节；674 个包成员，61 个素材完成注入和回读。
- `inspect`：主脚本、独立自定义脚本和触发器存在；依赖为虚空之遗战役及 `bnet:BOTC1/1.0/188805`。
- 原始基线 `base/BOTC.map` 的 SHA256 未变化；源码保留原 BOM 和 CRLF。
- `work/verify_log_delivery.py` 负责独立回读、校验源码与包内脚本一致、检查初始化入口及 UI 成员，并通过原始源码哈希校验补丁。它还执行旧增量函数，复现混合来源漏记和首下标检测失效。

这些测试不模拟 Galaxy 虚拟机指令上限、原生文本排版、实际 UI 消耗或网络同步，不把 JavaScript/Python 的耗时换算成游戏帧耗时。当前本机最新 `ScriptError` 是 11 月 12 日的旧测试日志，不能代表本次修复后的版本。

加载预算采用保守值：长历史会逐步出现，窗口先打开。单人 3600 条公聊在无其他工作时约需 28 游戏秒；13 人同时各加载 3600 条约需 92 游戏秒。这是按条数与定时周期算出的上界场景估计，不是实机测量。筛选目标稀少时，首次出现匹配内容也可能较慢。

已有的存储保留策略仍生效：公聊、个人私聊和投票超过容量仍按原规则淘汰旧段；全部私聊保留最近 1500 条。已被存储淘汰、且尚未来得及读取的记录无法恢复。界面仍使用原来的 20000 项上限。本次没有将全局存储改成无限保留。

复盘的白天私聊收集仍沿用原有收集函数，常驻聊天窗的文字转换也仍有成本；如候选版仍卡死，应优先取当局引擎错误和触发器调用栈，再定位后续路径。
