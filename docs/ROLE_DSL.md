# 角色一句话生成与规则 DSL

目标不是让模型直接写 Galaxy，而是把玩家的一句话稳定转换成可审计的角色规格。
模型只能生成 DSL 草稿，工具负责校验、生成接入计划和测试清单，代码仍由实现者确认。

## 工作流

1. 玩家提交一句话描述。
2. 使用提示词让任意大模型输出 `schema_version=2` 的 JSON。
3. 用 `botc.py design validate` 校验枚举、目标、持续时间和缺失字段。
4. 用 `botc.py design compile` 生成角色数据、必须接入的函数和测试清单。
5. 实现者补齐描述中未明确的内容，并通过 `role audit`、源码检查和构建。

```powershell
tools\botc.cmd design prompt "每个夜晚，你要选择一名玩家：你得知他是否是爪牙。"
tools\botc.cmd design validate roles\role_dsl.example.json
tools\botc.cmd design compile roles\role_dsl.example.json --out role_plan.md
```

## 为什么不用模型直接写 Galaxy

《血染钟楼》的角色差异通常集中在很小的词：

- “一名玩家”与“一名存活玩家”
- “你得知”与“他得知”
- “直到黎明”与“直到黄昏”
- “每局一次”与“每天一次”
- “选择”与“被选择”
- “死亡”与“被恶魔杀死”

这些差异会改变目标校验、token 生命周期、能力来源、胜负判断和相克规则。
因此自然语言必须经过受约束的中间层，不能让模型直接生成不可审计的几百行代码。

## DSL 原则

- `text` 保存玩家看到的规范描述。
- `lore` 保存角色介绍和玩法定位。
- `timing` 保存触发时机。
- `target` 明确定义数量、存活、本人、重复和目标类型。
- `effects` 只使用能力原语；无法表达时使用 `custom` 并人工审核。
- `frequency` 驱动一次性字段和重置逻辑。
- `night_order` 驱动自动唤醒，不把触发型角色塞进普通夜序；未确认具体行号时必须记录同类锚点。
- `tokens` 保存 token 名称、短名、作用、放置时机、移除时机、可见性和图标。
- `jinxes` 保存角色相克对象及结算说明。
- `artwork` 保存身份图、夜序图、token 图来源和成品文件名。
- `tests` 是接入验收的一部分，不是可选文档。

## 夜间顺序规范

先按能力语义归类，再以官方夜间顺序表中的现有角色为锚点插入：

| 分类 | 作用 | 典型角色 |
| --- | --- | --- |
| `rules` | 开局设置、规则改写、全局条件 | 提丰之首、卡扎力、科学怪人、罂粟种植者 |
| `role_change` | 身份、阵营、认知或能力来源改变 | 哲学家、舞蛇人、麻脸巫婆、帽匠、理发师 |
| `interference` | 中毒、保护、限制、强制选择及其他非直接击杀的状态干预 | 投毒者、水手、旅店老板、侍臣、赌徒、僧侣、魔鬼代言人、女巫、洗脑师、驱魔人 |
| `kill` | 恶魔行动及直接造成死亡的刀人能力 | 小恶魔、刺客、教父、造谣者 |
| `information` | 主要产出身份、人数、阵营或历史信息 | 占卜师、共情者、守鸦人、送葬者、侍女 |
| `utility` | 无法归入上述类别、但仍参与夜间结算的功能位 | 按现有官方表中最接近的能力选择锚点 |

粗粒度阶段是：

1. `rules`
2. `role_change` 与 `interference` 交错段
3. `kill`
4. `information` 与 `utility`

官方表并不是整齐的六段。`role_change` 和 `interference` 会交错，
例如麻脸巫婆早于投毒者，而水手又早于麻脸巫婆。
因此分类只决定大方向，最终位置必须查最新官方夜间顺序表，
并以同类角色、能力读写依赖和实际结算先后为依据。
分类按能力效果决定，不按阵营决定：爪牙的投毒、限制或保护能力归入
`interference`，只有直接造成死亡的爪牙能力才归入 `kill`。

若用户未指定具体夜序怎么办：

- 先确定角色属于哪个分类，再选一个能力最接近的现有角色作为 `anchor_role`。
- 用 `relation=before/after/near` 记录相对位置，不从零开始猜具体行号。
- 只有用户明确指定或已核对官方表后，才填写 `first` / `other` 的正整数行号。
- 如果它读取本夜其他角色的选择或身份变化，必须排在其后。
- 如果它提供的信息会被其他角色读取，必须排在其前。
- 不把触发型能力硬塞进普通夜序。
- 同时填写首夜和次夜起顺序；不行动的一侧填 `null`。

## Token 必填信息

每个 token 都必须说明：

- token id。
- token 名称与短名。
- 它改变什么规则或为哪个能力提供记录。
- 放置时机和放置者。
- 移除时机。
- 可见范围：说书人、持有者、公开或隐藏。
- 对应 token 图标成品文件名。
- 同一目标重复放置时覆盖、叠加还是忽略。
- 来源离场、换座位、死亡、跨日和第二局如何处理。
